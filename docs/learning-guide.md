# 推荐系统教学手册：从 0 到能讲清楚这个项目

> 读法建议：第 1–2 节先建立"为什么这么设计"的直觉，第 3–5 节是核心算法（面试主要问这里），
> 第 6 节是评估口径（**这个项目最值钱的部分**），第 7 节是工程细节，第 8 节是"自己动手改"。

---

## 1. 为什么推荐系统要分「召回 → 排序」两阶段

假设你有 100 万件商品、10 万用户。给一个用户算"他对每件商品的兴趣分"，需要 10 亿次打分。
如果一次打分是一个 200 层深度的神经网络，线上要在 50ms 内返回结果——算力根本不够。

所以工业界把它拆成两步：

| 阶段 | 输入 | 输出 | 模型特点 | 约束 |
|---|---|---|---|---|
| 召回 | 全库 100 万 → 500 个 | 候选集 | 简单、可离线预计算、可向量检索 | 必须毫秒级、必须能并行 |
| 排序 | 500 个 → 10 个 | 精排分数 | 复杂、特征多、可在线算 | 可以承受更贵的计算 |

**召回的 KPI 不是"准"，而是"别漏"**：只要目标物品在 500 个候选里，排序阶段就有机会把它捞上来。
所以召回看 Recall@500，排序看 NDCG@10 / AUC。

这个项目就是按这个结构搭的：四个召回模型 → Top-500 候选 → 四个排序模型 → Top-10。

## 2. 数据切分：为什么必须是「时间切分」

想象你要预测 2026 年的电影推荐效果。你有 2000–2003 年的评分数据。

**错误的做法（随机切分）**：把所有评分打乱，80% 训练、20% 测试。
问题：用户在 2001 年给《泰坦尼克号》打了 5 分，这条在训练集；
他在 2002 年又给同一部电影（或者同类电影）打了 5 分，这条在测试集。
模型只要记住"这个用户喜欢这类电影"就能答对，**但它学到的东西在真实场景里用不上**——
上线时你不可能拿到未来的数据。

**正确的做法（时间切分）**：按时间排序，前 80% 训练、后 20% 测试。
模型只能用"过去"预测"未来"，和线上完全一致。

本项目里这两种切分的差距是 **20.53% vs 10.94%**（Recall@20，同一个 BPR 模型）。
也就是说，随机切分会把你简历上的数字抬高接近一倍。

还有一个细节：**测试窗里每个用户可能有多条评分**。如果全拿来当目标，重度用户有 82 个目标、
轻度用户只有 1 个，指标会被重度用户主导。所以本项目统一取**窗内最早的一条**作为目标
（叫 next-item 协议），保证"每人 1 个目标"，和留一法口径可比。

## 3. 四个召回模型，各自在干什么

### 3.1 Popularity（流行度）：基线，但必须有

给每个用户推"全站最热的 20 部电影"，所有人推的一样。

它的意义不是效果，而是**标尺**：任何模型如果打不过流行度，说明它什么都没学到。
本项目的流行度 Recall@20 = 1.22%——这就是"闭着眼睛推"的水平。

它还有个副作用值得注意：覆盖率只有 1.35%（3706 部电影只推了 50 部），
Gini 系数 0.563，长尾占比 62.6%。**"最热"意味着"最集中"**。

### 3.2 ItemCF（基于物品的协同过滤）：经典，但怕稀疏

核心思想：**"看了 A 的人也看了 B"**。

1. 把每个物品表示成"哪些用户交互过它"的向量；
2. 算物品两两余弦相似度，每个物品只保留最相似的 200 个邻居（稀疏化）；
3. 用户的历史物品 × 相似度矩阵 = 该用户对所有物品的分数。

优点：可解释（"因为你看了 X"）、不需要训练、新用户只要有 1 条历史就能用。
缺点：**只会在热门区域打转**——相似度高的往往是本来就热门的物品。

数据印证：ItemCF 覆盖率 19.97%，但 Gini 高达 0.801（比流行度还集中），长尾占比只有 1.8%。
**准确率上去了，多样性崩了。**

### 3.3 BPR-MF：本项目的冠军

BPR = Bayesian Personalized Ranking（贝叶斯个性化排序），是一篇 2009 年的经典论文。

它不预测"打几分"，而是学**相对偏好**：对用户 u，正样本 i（他交互过）应该比负样本 j（他没交互过）
得分更高。损失函数：

```
L = -Σ log σ( x̂_ui - x̂_uj ) + λ‖Θ‖²
```

其中 `x̂_ui = p_u · q_i`（用户隐向量点积物品隐向量）。

**为什么要用 pairwise 而不是 pointwise？**
因为推荐场景里我们只观察到"用户交互了什么"，没观察到"用户不喜欢什么"。
把没交互的都当负例做二分类（pointwise）会被"用户没看到"污染；
pairwise 只要求"交互过的 > 没交互的"，对这个噪声更鲁棒。

实现要点（本项目 `retrieval.py`）：

```python
# 每个正样本配一个随机负样本
neg = rng.integers(0, n_items, size=len(sel))
x_ui = (U[u] * V[i]).sum(1)
x_uj = (U[u] * V[neg]).sum(1)
loss = -F.logsigmoid(x_ui - x_uj).mean() + reg * (...)
```

本项目配置：64 维、12 epoch、batch 4096、Adam lr 1e-3，CPU 上 42 秒训完。

**结果：Recall@20 = 10.94%，是流行度的 9 倍、ItemCF 的 2 倍，同时 Gini 0.668 比 ItemCF 更健康。**
这就是它成为冠军的原因——**准确率和多样性同时更好**，不是靠牺牲一个换另一个。

### 3.4 Two-Tower（双塔）：工业界主力，但在这个数据上不划算

结构：用户塔（用户 ID embedding + 历史物品向量均值）和物品塔（物品 ID embedding + 流派 one-hot 投影），
各自过一个 MLP，输出同维向量，用**内积**表示兴趣强度。

训练用 **in-batch softmax**：一个 batch 里 4096 条 (用户, 物品) 对，
对第 i 个用户，第 i 个物品是正例，**其余 4095 个物品全部当负例**。
这比逐条采样负例高效得多（一次前向得到 4096 个负例）。

但这里有两个坑，本项目都踩过并修好了：

**坑 1：用户塔和物品塔不在同一个空间。**
最初用户塔聚合的是 `item_emb`，物品塔用的是 `item_emb + genre_proj(genre)`。
两个向量在不同的坐标系里做内积，相似度没有意义——Recall@20 只有 3.2%，比 ItemCF 还差。
修法：聚合时用**完整的物品向量**（`all_item_matrix()`），保证同空间。

**坑 2：in-batch 负例天然偏向热门。**
batch 是按交互采样出来的，热门物品出现频率高，被当成负例的次数也多，
softmax 会把热门物品的向量压小。标准解法是 **logQ 校正**：

```
logits[i][j] = (u_i · v_j) / τ - log q(j)
```

其中 `q(j)` 是物品 j 在训练集里的出现频率。这相当于把"采样分布"除回去。

**坑 3：温度不能学。**
最初把温度设成可学习参数，它从 0.07 一路降到 0.036，softmax 变成近似 one-hot，
梯度消失，召回反而变差。改成固定 0.07。

即使修完这三个坑，双塔最终 Recall@20 = 9.45%，仍然比 BPR 低 1.5 个点，代价是 26 倍训练时间
（93 秒/epoch vs 3.5 秒）。但在判断"值不值得"之前，先看它的另两个数字：

- **覆盖率 52.2%**（BPR 46.4%），**Gini 0.639**（四个模型最低），长尾占比 17.9%；
- 在低活跃用户上（<5 条、5–20 条）它和 BPR 完全打平（12.5%、12.09%），说明隐向量泛化是有效的。

所以准确的结论不是"双塔不行"，而是：**在准确率上它用 26 倍成本换 1.5 个点差距换不回来，
但它换来了更好的曝光结构；如果业务方在意长尾生态，这个取舍就反过来了。**
这种"要看约束条件"的结论，比"XX 模型最好"值钱得多。

**为什么还要写"失败"？** 因为面试官听到"我试了双塔，它用 26 倍成本只换回 1.5 个点的差距，
但曝光结构更好，所以我按业务目标取舍"，比听到"我用了最先进的双塔模型"有价值得多——
前者说明你会判断，后者只说明你会调库。

## 4. 评估指标：别只会看 Accuracy

### 4.1 Recall@K

前 K 个推荐里，命中了几个真实目标。

```
Recall@K = (命中数) / (目标总数)
```

本项目每人 1 个目标，所以 Recall@20 ≈ "20 个里有没有中" 的平均值。

### 4.2 NDCG@K：考虑位置

Recall 不区分"命中在第 1 位"和"命中在第 20 位"。NDCG 给靠前的命中更高权重：

```
DCG@K  = Σ (2^rel_i - 1) / log2(i + 1)
NDCG@K = DCG@K / IDCG@K     （IDCG 是理想排序的 DCG）
```

### 4.3 覆盖率 / Gini / 长尾占比：多样性指标

- **Coverage@K**：所有用户的推荐里出现了多少比例的物品。1.35% 意味着 3706 部电影只推了 50 部。
- **Gini**：曝光分布的集中度，0 = 完全均匀，1 = 全部集中在一个物品。
- **长尾占比**：推荐里属于"后 80% 冷门物品"的比例。

**为什么要在简历/报告里写这三个？** 因为它们证明你理解推荐系统的真实目标——
不是"把最热门的推给所有人"，而是"在准确和多样之间找平衡"。
很多候选人只会写 Recall，一问"你的模型是不是只推热门"就答不上来。

### 4.4 AUC / LogLoss / ECE：排序阶段的三个视角

| 指标 | 回答什么问题 | 陷阱 |
|---|---|---|
| AUC | 排序能力：正例排在负例前面的概率 | 对类别不平衡不敏感，1:99 时也能到 0.89 |
| LogLoss | 概率预测的准确度 | 对极端错误惩罚重，受校准影响 |
| ECE | 校准：预测 0.1 的样本里是不是真有 10% 正例 | 正例率极低时绝对值天然很小，要看分桶曲线 |

本项目的坑：正例率只有 1%，所有模型 ECE 都 < 0.05，看起来"校准完美"。
实际上是因为模型输出都挤在 0.01 附近，**绝对误差天然小**。
正确的看法是图 08 的分桶可靠性曲线：中间几档样本少，曲线会抖。

## 5. 排序模型：LR / GBDT / FM / DeepFM

### 5.1 特征（`features.py`）

稠密特征 16 列：用户活跃度、物品热度、用户平均分、物品平均分、评分方差、物品年龄、
流派亲和度、流派余弦相似度、热度×活跃度交叉、召回分数……

稀疏特征 7 列：user_id、item_id、gender、age、occupation、year_bucket、genre_top。

**交叉特征是这个项目的重点**：
- `x_genre_affinity` = 用户流派偏好向量（中心化后）× 物品流派向量，点积；
- `x_pop_x_activity` = log(1+物品热度) × log(1+用户活跃度)，捕捉"活跃用户更愿意尝试热门"；
- `retrieval_score` = 召回阶段的分数，作为排序特征（**这就是"召回→排序"的串联**）。

### 5.2 四个模型

| 模型 | 原理 | 本项目结果 |
|---|---|---|
| LR | 线性 + one-hot，可解释 | AUC 0.8833 |
| GBDT | 树集成，自动做特征交叉与分箱 | **AUC 0.8903（最好）** |
| FM | 二阶交叉：`w0 + Σw_ix_i + ΣΣ<v_i,v_j>x_ix_j` | AUC 0.8416（最差） |
| DeepFM | FM + MLP，共享 embedding | AUC 0.8595 |

**为什么 FM 最差？** 因为本项目的特征里已经手工做了交叉（流派亲和度就是内积），
FM 的二阶项没带来新信息，反而因为稀疏字段多（用户/物品 ID 上千类）而过拟合。

**为什么 GBDT 只比 LR 高 0.7 个点？** 说明**特征工程比模型结构重要**。
这是一个可以在面试里直接讲的判断："我试了四个模型，差距不到 1 个 AUC 点，
所以我不会为了 0.7 个点上线一个需要 GPU 的 DeepFM。"

### 5.3 一个容易忽略的坑：按用户切分

CTR 样本是"用户 × 物品"对。如果随机切分样本，同一个用户会同时出现在训练和测试里，
模型只要背下"这个用户 ID 的 embedding"就能答对——AUC 会虚高很多。
所以本项目**按用户切**：70% 用户训练、30% 用户评估。

这和 5.1 的"时间切分"是同一个思想：**评估集必须模拟真实场景里"没见过的对象"**。

## 6. 这个项目最值钱的部分：评估口径诊断

### 6.1 切分偏差（图 03）

见第 2 节。随机切分 20.53% vs 时间切分 10.94%，**虚高 87.7%**。

### 6.2 采样偏差（图 04）

工业界常用 1:99 负采样算指标，因为全库打分太慢。但采样会改变指标的含义：

| 模型 | 全库 | 1:99 采样 | 虚高 |
|---|---|---|---|
| Popularity | 1.22% | 19.77% | ×16.1 |
| ItemCF | 5.34% | 52.58% | ×9.9 |
| BPR | 10.94% | 66.49% | ×6.1 |
| 双塔 | 9.45% | 65.09% | ×6.9 |

**注意：虚高倍数不是常数**，模型越强虚高越少（因为强模型本来就能把正例排进前 20，
采样只是把"排不进前 20"的失败案例删掉了一部分）。所以你不能用"采样指标 × 某个系数"
去反推全库指标——**必须自己算一遍全库**。

### 6.3 冷启动分层（图 09）

按训练集互动数分桶，看每个桶的 Recall。结论：BPR 在最冷的桶（<5 条）反而最高（12.5%），
ItemCF 掉到 0——因为它算不出相似度。

**回答"你的模型对冷启动用户友好吗"这个问题时，这张表就是答案。**

## 7. 工程细节（面试常问"你遇到过什么问题"）

### 7.1 稀疏矩阵聚合：慢 10 倍的坑

双塔训练时，每个用户的历史向量均值需要聚合。最初的写法是逐 batch、逐用户用 numpy 取平均，
一个 epoch 要十几分钟。改成：

```python
H = 行归一化的稀疏矩阵 (n_users × n_items)
hist_means = H @ item_matrix        # 一次矩阵乘法算完所有人
```

一个 epoch 从十几分钟降到 70 秒。

### 7.2 缓存：调排序层时不该重跑召回

双塔训练 14 分钟。如果每次调 CTR 特征都重跑，一天只能试 3 次。
所以召回分数存成 `outputs/cache/retrieval_scores.npz`（39MB），`--no-cache` 才重训。

### 7.3 复现：所有随机源都固定

`RANDOM_STATE = 20261106` 贯穿 numpy / torch / sklearn，数据切分、负采样、模型初始化全部用它。
同一台机器上跑两次，指标完全一致。

### 7.4 测试：12 个单元测试

`tests/test_metrics.py` 覆盖 Recall / NDCG / MRR / 覆盖率 / Gini / AUC / ECE / Bootstrap CI
的边界情况（空目标、全部命中、K 大于候选数）；`tests/test_splits.py` 覆盖三种切分的正确性
（不重叠、时间顺序、每用户 1 目标）。

CI（`.github/workflows/tests.yml`）在 GitHub Actions 上跑 pytest。

## 8. 自己动手：五个可以改的地方

1. **换数据**：MovieLens-25M 已经在 `prepare_data.py` 里留了入口。数据量大 25 倍，双塔可能就跑赢 BPR 了——
   这正是"数据规模决定模型选择"的实验。
2. **加召回模型**：`retrieval.py` 里照着 `ItemCFRecommender` 的接口写一个 `EASE` 或 `SASRec`，
   在 `run_all.py` 的 `MODEL_NAMES` 里加一行。
3. **改评估**：把 `MAIN_K` 从 20 改成 50，看排名会不会变（通常不会，但会放大绝对差距）。
4. **加特征**：`features.py` 的 `DENSE_COLS` 加一列"用户评分时间间隔"，看 AUC 变化。
5. **换损失**：BPR 换成 softmax 交叉熵（多负例），看 recall 是否提升。

每改一处，**先想清楚"我预期指标怎么变、为什么"**，再跑。这个习惯比会调参重要得多。

## 9. 一页速查：面试时怎么讲这个项目

**30 秒版**：
> 我用 MovieLens-1M 搭了一个两阶段推荐系统，召回层对比了流行度、ItemCF、BPR-MF、双塔四个模型，
> 排序层对比了 LR、GBDT、FM、DeepFM。最有价值的不是模型本身，而是我做了三组评估口径的对照实验，
> 发现随机切分把指标抬高 1.9 倍、1:99 负采样抬高 6.1 倍——这说明很多公开的推荐指标是不可比的。

**被追问时**：
- "为什么 BPR 最好？" → pairwise 损失、隐向量表达、比 ItemCF 覆盖更均衡。
- "双塔为什么不行？" → 数据规模小、训练贵、优势在线上而非离线。
- "怎么证明你的评估是对的？" → 全库打分、时间切分、按用户切分、每人 1 目标、固定随机种子。
- "你遇到过什么坑？" → 双塔空间不一致、in-batch 负例偏热门（logQ）、温度坍缩、稀疏聚合慢 10 倍。

详见 `docs/interview-qa.md`（40 个问题）。
