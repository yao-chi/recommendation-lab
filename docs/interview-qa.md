# 面试问答：两阶段推荐系统项目

> 40 个问题，按面试官通常会问的顺序排列。答案里的数字都来自本仓库 `reports/results.json`。
> 建议：先背「一句话答案」，再看下面的「展开」——面试时先说一句，等对方追问再展开。

## A. 项目整体（1–6）

### Q1. 一句话介绍这个项目
**一句话**：我用 MovieLens-1M 搭了一个召回 + 排序的两阶段推荐系统，重点不在模型多复杂，
而在于把**离线评估的可信度**做成了实验——切分方式能差 1.9 倍，负采样能差 6.1 倍。

**展开**：召回层 4 个模型（流行度 / ItemCF / BPR-MF / 双塔），排序层 4 个（LR / GBDT / FM / DeepFM），
外加三组诊断实验（切分偏差、采样偏差、冷启动）。全流程 CPU 15 分钟，一条命令复现。

### Q2. 为什么选 MovieLens-1M？
- 有**真实时间戳**，能做时间切分（MovieLens-100K 也有，但 1M 的规模更适合跑深度学习）；
- 有用户画像（性别/年龄/职业）和物品流派，能构造交叉特征；
- 学术界公认，指标可对比，不会像用公司数据那样"无法验证"；
- 100 万条在 CPU 上能跑完，不需要 GPU。

**为什么不选 Criteo/Avazu？** 我试过，下载需要登录或被 403，拿不到数据。
退而用 MovieLens 的"是否交互"构造 CTR 样本——虽然不如真实曝光日志，但**方法链路是完整的**，
这一点我在 README 里写清楚了。

### Q3. 项目的技术难点是什么？
不是模型，是**评估**。三个坑：
1. 随机切分导致信息泄漏，指标虚高 87.7%；
2. 1:99 负采样让 Recall@20 从 10.94% 变成 66.49%，而且**虚高倍数随模型变化**，不能换算；
3. 双塔实现里用户塔和物品塔不在同一个向量空间，召回只有 3.2%，排查了两轮才定位。

### Q4. 你在这个项目里最大的收获？
**"指标好看"和"系统有用"是两件事。** 我一开始也被 20% 的随机切分 recall 迷惑过，
后来做了对照实验才发现那个数字没有意义。现在我拿到任何推荐指标，第一反应是问：
怎么切的、候选集多大、每人几个目标。

### Q5. 如果给你更多时间，你会做什么？
三件事，按优先级：
1. **换 25M 数据重跑双塔**——验证"数据规模决定模型选择"这个假设（25 倍数据，双塔可能翻盘）；
2. **加序列模型**（SASRec / BERT4Rec），因为 MovieLens 有时间顺序，序列信息目前没用上；
3. **做在线 A/B 的模拟**：用时间切分的后 20% 做"线上"，模拟不同策略的累积收益（CTR/CVR），
   而不只是离线 NDCG。

### Q6. 这个项目是你独立做的吗？数据哪来的？
独立完成。数据是 GroupLens 官方公开发布的 MovieLens-1M，用于科研教学，仓库里不放数据本体，
`prepare_data.py` 会自动下载并校验 SHA-256。

## B. 召回层（7–18）

### Q7. 为什么要分召回和排序？不能一步到位吗？
算力。100 万物品 × 10 万用户，精排模型一次打分要几十毫秒，全库打分要几小时。
召回用轻量模型（或向量检索）把候选缩到几百个，排序再用重模型精算。
**召回的 KPI 是"别漏"（Recall@500），排序的 KPI 是"排得准"（NDCG@10）。**

### Q8. 你的召回评估为什么用全库而不是采样？
因为采样会改变指标含义。同样一个 BPR 模型，全库 Recall@20 = 10.94%，1:99 采样 = 66.49%。
采样把"从 3706 个里挑 20 个"变成"从 100 个里挑 20 个"，分母小了 37 倍。
**我做全库评估，虽然慢（每个用户 3706 次打分），但数字是真的。**

### Q9. BPR 的损失函数是什么？为什么用 pairwise？
```
L = -Σ log σ(x̂_ui - x̂_uj) + λ‖Θ‖²
```
只用"用户交互过的物品 > 没交互的物品"这个相对关系，不要求预测具体分数。
好处：推荐场景只有正反馈（点击/评分），没有"明确不喜欢"的负反馈；
把所有未交互当负例做 pointwise 会被"用户没看到"污染，pairwise 对这个噪声更鲁棒。

### Q10. BPR 和矩阵分解（MF）什么关系？
BPR 是 MF 的**排序版**。MF 用均方误差拟合评分（pointwise 回归），BPR 用 pairwise 排序损失。
在隐式反馈（只有"交互/没交互"）场景，BPR 通常更好；在有显式评分且关心评分预测时，MF 更合适。
本项目用的是隐式反馈（是否评分），所以选 BPR。

### Q11. BPR 的负样本怎么采？有优化空间吗？
本项目是**均匀随机采**（`rng.integers(0, n_items)`）。
可以改进的方向：
- **按热度采样**（热门物品更容易被当负例，但需要重要性校正，否则会把热门压死）；
- **难负例挖掘**（用当前模型打分高的未交互物品当负例），收敛更快但容易过拟合；
- **batch 内负采样**（双塔就是这么做的）。

### Q12. ItemCF 的原理？为什么它覆盖率低？
"看了 A 的人也看了 B"。把物品表示成用户集合的向量，算余弦相似度，取 Top-200 邻居，
用户历史加权求和得到分数。

覆盖率低（19.97%）且 Gini 高（0.801）的原因：**相似度矩阵天然聚集在热门物品上**——
热门物品和谁都相似，冷门物品只和少数物品相似。所以推荐结果总是在热门区打转，
长尾占比只有 1.8%。

### Q13. 双塔模型的结构？
- 用户塔：用户 ID embedding + 历史物品向量的均值（行归一化的稀疏矩阵一次乘完）+ MLP；
- 物品塔：物品 ID embedding + 流派 one-hot 的线性投影 + MLP；
- 两塔输出归一化后的向量，用**内积**表示兴趣强度。

**为什么用内积而不是 concat + MLP？** 因为内积可以预计算物品向量、用 FAISS 做近似最近邻，
线上延迟低。这是双塔存在的唯一理由。

### Q14. in-batch softmax 是什么？有什么问题？
一个 batch 里 4096 个 (用户, 物品) 对，对第 i 个用户，第 i 个物品是正例，其余 4095 个都是负例。
一次前向得到 4095 个负例，比逐条采样高效。

**问题：负例分布不是均匀的，而是按曝光频率采样的**——热门物品被当负例的次数多，
softmax 会把它们的向量压小。解法是 **logQ 校正**：`logits -= log q(j)`，把采样分布除回去。

### Q15. 你的双塔和 BPR 差多少？差在哪？
最终 Recall@20：BPR 10.94%，双塔 9.45%，差 1.5 个点；但双塔训练 93 秒/epoch，是 BPR 的 26 倍。
三个原因：
1. **数据规模**：80 万条交互，双塔需要亿级才能发挥；
2. **训练成本**：12 epoch 远没收敛，再加 epoch 成本无法接受；
3. **离线评估体现不出双塔优势**：它的价值在"物品向量可预计算、支持向量检索、新物品增量上线"，
   这些在离线全库打分里看不出来。

**但它换回了更好的曝光结构**：覆盖率 52.2% vs 46.4%，Gini 0.639 vs 0.668，长尾占比 17.9% vs 14.9%。
**所以我的判断是：追求准确率选 BPR，追求长尾生态和可插拔新物品选双塔**——这取决于业务目标，
不是一句"哪个模型更好"能回答的。

### Q16. 双塔训练时温度为什么要固定？
我最初把温度设为可学习参数（初始 0.07），它一路降到 0.036，softmax 变成近似 one-hot，
正负例的梯度差距消失，模型学不动，召回反而下降。
固定 0.07 之后正常。**教训：可学习参数不是越多越好，要理解它在优化什么。**

### Q17. 双塔里"用户历史向量均值"是怎么算的？
构造一个行归一化的稀疏矩阵 `H`（n_users × n_items，每行是该用户历史物品的 1/|hist|），
每个 epoch 开始算一次 `H @ item_matrix`，得到所有用户的历史均值。
最初是逐 batch 用 numpy 算，一个 epoch 十几分钟；改成矩阵乘法后 70 秒，**快 10 倍以上**。

### Q18. 冷启动用户你的模型表现如何？
按训练集互动数分桶（<5 / 5–20 / 20–50 / ≥50）：
BPR 在 <5 条的桶里 Recall@20 = 12.5%，ItemCF = 0%（算不出相似度），流行度 = 0%（这 8 个用户的目标太冷门）。
**BPR 靠隐向量泛化，对小样本更宽容**——这是"用 embedding 换鲁棒性"的直接证据。

## C. 排序层（19–28）

### Q19. 排序阶段用了哪些特征？
- 稠密 16 列：用户活跃度/平均分/评分方差、物品热度/平均分/年龄、流派亲和度、流派余弦、
  热度×活跃度、物品年龄、召回分数；
- 稀疏 7 列：user_id、item_id、性别、年龄、职业、年代桶、主流派；
- 交叉项 4 个，其中 `x_genre_affinity` 是"用户流派偏好向量（中心化）× 物品流派向量"的点积。

**召回分数作为排序特征**，这是两阶段串联的关键——排序模型知道"召回阶段有多确信"。

### Q20. 为什么 CTR 样本要按用户切分？
如果随机切样本，同一个用户同时出现在训练和测试里，模型背下"用户 ID 的 embedding"就能答对，
AUC 虚高。按用户切（70% 用户训练、30% 评估）才模拟"没见过的新用户"。
**这和召回层用时间切分是同一个思想：评估集必须模拟真实场景。**

### Q21. 四个排序模型的结果？为什么 GBDT 最好？
AUC：GBDT 0.8903 > LR 0.8833 > DeepFM 0.8595 > FM 0.8416。
GBDT 好是因为它能自动做特征交叉和分箱，对稀疏 ID 特征的处理比线性模型灵活。
但**只比 LR 高 0.7 个点**，说明特征工程比模型结构重要。

### Q22. 为什么 DeepFM 没跑赢 GBDT？
- 数据量小（8 万条训练样本），深度模型容易过拟合；
- 特征里已经手工做了交叉（流派亲和度），DeepFM 的自动交叉没带来新信息；
- GBDT 在表格数据上本来就是强基线。

**如果数据到千万级、特征到几百维，DeepFM 可能会赢。** 这个判断比"我用了 DeepFM"更有价值。

### Q23. FM 的公式？为什么它比 LR 强/弱？
```
ŷ = w0 + Σ w_i x_i + ΣΣ <v_i, v_j> x_i x_j
```
它用隐向量内积表示二阶交叉，参数量从 O(n²) 降到 O(nk)。
本项目 FM 单独用最差（0.8416），因为特征里已经有手工交叉，FM 的二阶项没带来增量，
反而因为稀疏 ID 字段多（用户 6040 类、物品 3706 类）而过拟合。

### Q24. AUC 0.89 算好吗？
在 1:99 的候选集上算正常偏好。但 **AUC 高不代表排序好**——它衡量的是"正例排在负例前面的概率"，
不关心排在第 1 还是第 100。真正该看的是 NDCG@10（本项目 0.7115）和线上 CTR。

### Q25. ECE 是什么？为什么你的 ECE 都这么小？
ECE = 期望校准误差：把预测概率分桶，比较"预测均值"和"实际正例率"。
本项目 ECE 都 < 0.05，看起来完美——**但这是因为正例率只有 1%，模型输出都挤在 0.01 附近，
绝对误差天然小**。正确的看法是可靠性曲线（图 08），看中间几档是否贴合。

### Q26. 排序阶段怎么评估"业务价值"？
离线只能看 AUC/NDCG。真正的业务价值要看：
- 线上 CTR / CVR 提升；
- 多样性（推荐里有多少不同物品/流派）；
- 长期留存（推得太窄会让用户疲劳）。
本项目只能做离线，所以我把多样性指标（覆盖率/Gini/长尾）也放进来了，
**因为"准确但单一"的推荐在真实业务里是负收益**。

### Q27. 你怎么处理类别特征？
手写 `FieldEncoder`：每个字段建"值 → 下标"映射，全局 one-hot 用偏移量拼接
（`offset[field] + code`）。没用 sklearn 的 `OneHotEncoder`，因为百万级稀疏矩阵它的内存开销太大。
GBDT 用整数编码 + 原生 categorical 分裂（只对 ≤255 类的字段，避免 sklearn 的基数上限报错）。

### Q28. 排序模型的推理延迟考虑过吗？
离线没测。但如果上线：LR 最快（一次点积），GBDT 次之（树深度 6，300 棵），
DeepFM 最慢（要过 MLP）。**在 AUC 只差 0.7 个点的情况下，我会选 GBDT 或 LR，不会选 DeepFM。**

## D. 评估与实验设计（29–35）

### Q29. 为什么时间切分比随机切分低这么多？
随机切分让模型在训练时见过"未来的"交互。同一用户在时间上相邻的评分高度相关
（刚看完 A 觉得好，接着看同类的 B 也给高分），信息从测试集漏进训练集。
时间切分强制"用过去预测未来"，和线上一致。
**数字：20.53% vs 10.94%，虚高 87.7%。**

### Q30. 留一法和时间切分差多少？
10.63% vs 10.94%，基本一致（差 2.8%）。因为留一法也是"用历史预测下一条"，
只是不保证全局时间顺序。**这说明只要不用随机切分，指标量级就是可信的。**

### Q31. 1:99 负采样为什么会让指标虚高？
候选集从 3706 个缩到 100 个，分母小 37 倍。正例本来能排进前 200 的，在 100 个候选里就排进前 20 了。
**而且虚高倍数不是常数**：流行度 ×16.1、ItemCF ×9.9、BPR ×6.1——
模型越强虚高越少（强模型本来就不依赖采样"删掉失败案例"）。
所以不能用"采样指标 × 系数"反推全库指标。

### Q32. 为什么每个用户只取 1 个目标？
如果测试窗里所有交互都当目标，重度用户有 82 个目标、轻度用户 1 个，
指标会被重度用户主导（他们的目标多、难命中）。
取"窗内最早一条"保证每人 1 个目标，和留一法口径一致，**指标可以在不同切分方式之间横向比较**。

### Q33. 你怎么保证结果可复现？
- `RANDOM_STATE = 20261106` 贯穿 numpy / torch / sklearn；
- 数据切分、负采样、模型初始化全部用它；
- 数据有 SHA-256 校验；
- 同一台机器跑两次，指标完全一致（我验证过）。

### Q34. 12 个单元测试测什么？
指标函数（Recall/NDCG/MRR/覆盖率/Gini/AUC/ECE/Bootstrap）的边界：空目标、全命中、K 大于候选数；
切分函数：训练/测试不重叠、时间顺序正确、每人 1 目标。
CI 在 GitHub Actions 上跑。

### Q35. 如果线上指标和离线不一致，你怎么排查？
1. 先看**数据分布**：线上候选集和离线是否一致（新物品、新用户比例）；
2. 看**特征可用性**：离线用了未来信息（比如物品的最终热度）没有？
3. 看**评估口径**：候选集大小、每人目标数、是否过滤已交互；
4. 做**分层对比**：新用户 vs 老用户、热门 vs 长尾，定位是哪个群体掉得厉害。

## E. 工程与代码（36–40）

### Q36. 代码结构怎么组织的？
```
src/reclab/    # 库：config / data / splits / metrics / retrieval / features / ranking / diagnostics / plots
scripts/       # 入口：prepare_data.py（下载校验）、run_all.py（全流程）
tests/         # 12 个单测
docs/          # 教学手册、面试问答、简历写法
```
**为什么分库和脚本？** 库可以被 notebook 或别的脚本复用，脚本只负责编排和打印。
面试官看代码时能一眼看出边界。

### Q37. 一条命令跑完全流程，具体做了什么？
数据体检 → 时间切分 → 4 个召回模型训练 + 全库打分 → 缓存 → 指标表 → CTR 样本 → 4 个排序模型 →
诊断（3 种切分 × BPR、采样偏差、冷启动分层）→ 10 张图 → `results.json`。
CPU 15 分钟，有缓存 90 秒。

### Q38. 你提到缓存，具体怎么做的？
召回分数存 `outputs/cache/retrieval_scores.npz`（39MB，4 个模型的分数矩阵）。
调排序层时不重跑召回；`--no-cache` 强制重训。**因为双塔训练 14 分钟，不缓存一天只能试 3 次。**

### Q39. 遇到过最难的 bug？
双塔召回只有 3.2%，比 ItemCF 还差。排查过程：
1. 先怀疑数据（检查了正负样本构造，没问题）；
2. 再怀疑超参（调了 lr、batch、维度，没改善）；
3. 最后 print 向量范数，发现**用户塔聚合的是 `item_emb`，物品塔用的是 `item_emb + genre_proj`**，
   两个向量不在同一空间，内积没有意义。
修完（统一用 `all_item_matrix()`）召回涨到 9.45%——离 BPR 只差 1.5 个点。
所以那个 bug 不是"模型不行"，而是"实现错了导致模型看起来不行"，这两个判断要分开。

### Q40. 这个项目如果上线，你会怎么部署？
- 召回：BPR 的物品向量离线算好，用 FAISS 建索引，线上一次查询 <10ms；
- 排序：GBDT 模型导出为 ONNX 或 pmml，特征实时拼装；
- 冷启动：新用户走流行度 + 流派偏好，新物品走内容相似度（流派 + 年代）；
- 监控：召回率（离线抽样）、CTR、覆盖率、长尾占比四周对比。
